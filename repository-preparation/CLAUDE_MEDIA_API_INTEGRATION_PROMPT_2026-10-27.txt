## Objective

Add a reusable, evidence-based way for future song productions to discover and selectively source video footage from these two public services:

1. Wikimedia Commons, through its public MediaWiki Action API at [https://commons.wikimedia.org/w/api.php](https://commons.wikimedia.org/w/api.php).
2. Internet Archive, including the Prelinger collection, through its public Advanced Search API and item metadata API.

Prelinger is a collection within Internet Archive. Do not add stock-library providers, an aggregator, a new renderer, a per-song API dependency, or a separate Remotion project.

The goal is a local discovery workflow that can accept a natural-language scene need, return a small ranked list of video candidates with previews and source evidence, verify item-level rights, and download only a deliberately selected file into that song’s own folder. The API adapters should serve the connected Remotion production workflow without becoming part of rendering or making external calls during render.

### Search and inspection behavior

- Accept a scene description and optional filters, including source, video MIME/container, approximate duration, minimum dimensions, date/era, and collection. Return a bounded, configurable number of results; do not crawl entire catalogs or bulk-download datasets.
- Search Commons through the Action API, in file namespace, and filter for actual video MIME/container types rather than assuming every file result is video. Request the file page URL and available `imageinfo`/`extmetadata`; expose original and thumbnail/preview URLs when present.
- Search Internet Archive’s Advanced Search for video records (`mediatype:movies`), with an optional `collection:prelinger` filter. Follow returned identifiers with the item metadata read endpoint to inspect item-level metadata and files. Identify a usable video file from actual MIME/format, size and duration metadata; do not assume the first file is the movie or that the download filename can be guessed.
- Do not make unsupported semantic-match claims. Show title, description/subjects, creator, date, source collection and why the result matched. A numeric score may sort results but must not imply the footage was visually inspected.
- Keep search/preview separate from `download`. API results should link to the original item page so a human can preview it in the existing browser workflow. Do not build a browser automation dependency or pretend metadata preview is visual inspection.
- Re-fetch a selected candidate’s metadata immediately before any later download, since search indexes and rights statements can change.
- Cache small metadata responses to reduce calls; set sensible timeouts and response-size limits; handle pagination, transient errors, 429/503, `Retry-After`, malformed JSON and unavailable media clearly. Do not bypass access controls or hotlink-protection mechanisms.

### Rights gate and attribution

The project’s default allowlist is only:

- Public Domain, with an explicit item-level basis;
- CC0;
- CC BY, with the exact license/version and attribution fields.

Do not accept CC BY-SA, NC, ND, “free,” “open,” blank, missing, conflicting or ambiguous rights as equivalent to this allowlist. Do not infer rights from the collection, uploader, repository, item age, API availability or a search result count. Do not treat Internet Archive or Prelinger as certifying rights: Internet Archive says item rights information is often supplied by uploaders and is not guaranteed. For any uncertain result, mark it `rights_unverified` and exclude it from download/production use until separately resolved. Do not characterize every Prelinger film as public domain.

For Commons, parse recognized machine-readable fields conservatively (`License`, `LicenseShortName`, `LicenseUrl`, `UsageTerms`, `Artist`, `Credit`, `AttributionRequired`, `Copyrighted` where present) and retain the raw relevant values. If the API omits or contradicts fields, link the file description page and mark the rights unresolved rather than guessing from free text.

For Internet Archive, preserve the exact item-level `licenseurl`, `rights` and related fields where supplied, the item page, collection, uploader/creator, and selected filename. Check the item page’s rights statement. Search-index omissions are not a license. Exclude results where rights cannot be established under the allowlist.

Generate an attribution string for every accepted CC BY asset containing creator/author, title, source link, license name/version and license link, plus a note of modifications. Preserve rights evidence for public-domain/CC0 items as well. Save a song-local machine-readable manifest and a readable `CLIP_MANIFEST.md` (or the existing equivalent) containing provider, item/file identifiers, title, creator/uploader, source and file URLs, rights text, license URL/version, access date, technical metadata, downloaded SHA-256, local path, exact in/out points if later trimmed, transformations and required attribution. Do not put attribution text on screen automatically; expose it for production credits and delivery notes, and let the song’s creative plan place credits appropriately.

### Selected download behavior

- Download only after a later explicit per-song selection, never as a side effect of search. For this implementation pass, do not download any asset.
- In the tool’s eventual `download` path, require the candidate’s rights status to pass the allowlist, use a safe deterministic destination under the selected `productions/<song>/public/archive/` (or current project convention), validate the response and expected type/size, calculate a checksum, and refuse to overwrite an existing file.
- Preserve the original downloaded file unchanged. Any later trimming, muting, crop, grade or transcode must be declared in the song manifest and performed only under that song’s authorized media stage.
- Do not fetch or rehost all search results. Respect source policies and cache metadata, not bulk media.
